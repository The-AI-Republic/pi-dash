# `@pidash/api-client` contracts — runbook (NEWFRONT-14)

One test per contract, each parsing a real response from a live local Django
(`apps/api`) seeded with `packages/api-client/contract/seed-contracts.py`.
Unit tests (`src/*.test.ts`) run everywhere with stub transports; the
contract suites (`src/contract/*.contract.test.ts`) skip unless
`PIDASH_CONTRACT_BASE_URL` is set, so CI stays green.

### Nested pages delta (NEWFRONT-833 → NEWFRONT-850 / PDASHOSS01-270)

The live OSS backend probed on 2026-10-22 does not yet serve the D17
nested surface from parity/specs/pages.md §11.7. The contracts accept it
(the nested fields are optional) and the live suite pins only what the
build answers today:

- `GET BASE/pages/?parent=<id>` is accepted but ignored: it answers the
  same top-level collection. The contract still sends the parameter.
- Page objects carry `parent` but no `parent_id` or `sub_pages_count`;
  the live suite asserts the fields are absent, so it will need updating
  (not failing silently) when the backend lands them.
- `POST BASE/pages/` with `parent` answers `404 "The required object does
not exist."` because the serializer cannot resolve the parent pk, even
  though the row is minted; the live suite asserts the 404 and cleans the
  stray row. `PATCH` accepts `parent` (including null).
- No self/descendant `400`, child-in-search, cascading archive, detach on
  unarchive, or delete re-homing can be observed until the backend lands.
- Backend probe for "landed" (§11.7): a create-with-parent answers 201,
  the children list contains the child, the child detail answers 200 and
  the parent carries a numeric `sub_pages_count`.

NEWFRONT-850 owns the nested slices and PDASHOSS01-270 the backend; both
re-run this suite and replace the absence assertions with the target
shape.

## From a clean checkout

Prerequisites: the JS toolchain (`pnpm install` at the repo root) and a
Python environment with the `apps/api` requirements installed.

```sh
# 1. Create a scratch database (never reuse a shared one).
createdb pidash_newfront14

# 2. Migrate and seed it. The script prints its target first, refuses
#    prod-like names, and writes nothing without --apply.
cd apps/api
export DATABASE_URL="postgres://<user>@localhost:5432/pidash_newfront14"
export REDIS_URL="redis://localhost:6379/0"
export AMQP_URL="redis://localhost:6379/1"
export WEB_URL="http://127.0.0.1:8123" APP_BASE_URL="http://127.0.0.1:8123"
export DJANGO_SETTINGS_MODULE="pi_dash.settings.local"
# Dummy object-store credentials: presigned-URL signing is local crypto, so
# the attachment suites need values present, not a reachable store.
export AWS_ACCESS_KEY_ID="contract-dummy" AWS_SECRET_ACCESS_KEY="contract-dummy"
export AWS_S3_BUCKET_NAME="contract-dummy" AWS_REGION="us-east-1"
python manage.py migrate
python ../../packages/api-client/contract/seed-contracts.py
python ../../packages/api-client/contract/seed-contracts.py --apply

# 3. Serve it on a port of your own (do not reuse another run's port).
#    uvicorn, not runserver: the chat event stream is an async view and
#    runserver consumes its infinite iterator synchronously (the stream
#    test hangs there). Serve the ASGI app instead.
python -m uvicorn pi_dash.asgi:application --host 127.0.0.1 --port 8123

# 4. Run the contract suites against it (from the repo root).
export PIDASH_CONTRACT_BASE_URL="http://127.0.0.1:8123"
pnpm --filter @pidash/api-client test
```

Expected: unit tests pass and all contract tests run (not skip) and pass — except the favorite-list GET (red until backend bug NEWFRONT-384 is fixed) and the chat close + chat accept-decide (red until backend bug PDASHOSS01-307 is fixed; the table above is the count).
Unset `PIDASH_CONTRACT_BASE_URL` returns the package to unit-only mode.

## Notes

- The suites sign in through the real form flow, so they prove the session
  cookie jar in `src/contract/setup.ts` end to end. The jar walks
  redirects itself because fetch hides the intermediate `Set-Cookie`
  headers (the sign-in 302 carries the session) — a browser keeps those.
- `AMQP_URL` must point at a reachable broker (local redis works): the
  issue list queues a visit-tracking task and 500s when the broker refuses
  connections. Most suites need only the broker, not a worker. The
  exception is the single-value delete clear case (NEWFRONT-737): the
  server clears affected items from a queued soft-delete sweep
  (`soft_delete_related_objects` nulls the item's estimate reference), so
  that one test needs `celery -A pi_dash worker` running against the same
  broker; without it the item keeps its deleted value's id and the test
  fails. The reassignment case needs no worker — its item update is inline.
- Seeded rows use a `contract-` prefix and `get_or_create`, so re-seeding is
  safe. The seed user password defaults to `Contract123!` and can be
  overridden with `PIDASH_CONTRACT_PASSWORD` (mirrored to the test run).
- The seed also mints a fixed-key desktop session row (no HTTP flow in this
  build stamps the desktop marker), whose key the desktop-gated suites send
  as the session cookie. Override the key with
  `PIDASH_CONTRACT_DESKTOP_SESSION_KEY` (mirrored to the test run).
- Profile issue tabs (NEWFRONT-570): the spec makes the saved filter and
  display reads/writes browser-local, scoped to workspace plus viewed
  member — there is no server route, so no contract exists for them. The
  workspace/project display prefs that do have routes are already covered
  by `getWorkspaceUserProperties` / `updateWorkspaceDisplayPreferences`
  and their project counterparts.
- The space suites (NEWFRONT-752) read a published board at the fixed anchor
  `contract-board-anchor`, minted by the seed on the seeded project with all
  three engagement flags on. Override with `PIDASH_CONTRACT_BOARD_ANCHOR`
  (mirrored to the test run).
- Spaces auth form posts redirect to `/spaces/...`, a frontend path the
  Django-only contract stack does not serve. Those suites post through
  `contractTransport(jar, { followRedirects: false })` and read the `Location`
  header, which is exactly what the browser's client ends up at.
- Validation is always on in tests (`validate: true` in the harness);
  production builds skip it (`NODE_ENV=production`).
- Anonymous auth endpoints share one 30/minute throttle per IP, so a full
  parallel `vitest run` trips 429s once the package holds this many
  suites (the sign-in then lands on a 200 failure page and every test in
  the file 401s). Run the live suites in batches of ~6 files with a
  minute between batches. Contract tests allow 30s per test
  (`testTimeout` in `vitest.config.ts`) because each write round-trips
  the broker; suites resolve seeded rows by name, never `results[0]`
  (newest-first reads a transient probe under parallel runs).
- Workspace webhook reads currently echo `secret_key` although the
  workspace-settings spec (§§20–22) says a read must never return the key.
  The read row (`WorkspaceWebhook`) declares no secret field, so the strict
  parse drops the leaked key before any caller sees it; the reveal still
  comes from the create and regenerate answers (`CreatedWorkspaceWebhook`,
  which requires the key). Noted for the webhooks slice (NEWFRONT-541) to
  fix the serializer.
- The GitHub connect and GitLab register endpoints verify the credential
  against the live provider, so the seed script plants a connected GitHub
  integration and two provider accounts directly. Those suites prove the
  reads, permissions, disconnect semantics and validation refusals; the
  success shapes of connect/register are pinned by unit stubs. The GitLab
  disconnect test is repeatable (the backend's disconnect is idempotent).
  The fixtures live in their own `contract-dev` workspace (override with
  `PIDASH_CONTRACT_DEV_WORKSPACE`), not the shared `contract-acme`, so the
  project-repository suite's "no provider account" 409 on the seeded
  workspace keeps holding.
- The epics-segment contracts (`src/contracts/epics.ts`) are cloud-only:
  the OSS backend serves no `epics/` routes, so they cannot be exercised
  by a live contract suite here. They mirror the issues CRUD surface with
  the `epics` service segment, renamed children (`epics/<id>/issues/`)
  and links (`epics/<id>/links/`) collections, and the shared
  `work-items/<id>/move/` move; stub tests in `contracts.test.ts` prove
  the URLs and shapes. Verify them against the cloud backend when it is
  reachable.
- The page live-ops suite (`pages-live.contract.test.ts`, NEWFRONT-834)
  needs a scratch apps/live next to the contract Django: serve Django
  first, then run the live server with `API_BASE_URL` at the Django
  origin, `LIVE_SERVER_SECRET_KEY` set, and `REDIS_URL` at a scratch
  redis, and export `PIDASH_CONTRACT_LIVE_URL` at the live origin. The
  suite signs in once and shares the jar between a Django client (probe
  pages, created and removed raw) and a live client, so the export's
  forwarded cookie resolves. Django needs no live wiring for it (page
  create stores no binary; the suite persists converted forms through
  the description PATCH like the PAGE-071 oracle does).
