Goal: build apps/web_new, a new React frontend that replaces apps/web, written independently and with the same functionality. It serves both web and the desktop app. apps/web stays running until each area has moved over.

Two goals, binding on every run:

1) Independent code: the old frontend is a reference, never a source.
- Never import from the old frontend: @pi-dash/* packages, apps/web/**, apps/web/ce/**, desktop-overlay/**, private ee-overlay/apps/web/**. No components, hooks, stores, services, utils, constants, types or styles.
- Never copy code, not even a snippet you then edit. Never translate an old file into the new stack while keeping its structure, names and control flow. Never copy class strings, CSS, message text, icons or assets.
- You may read the old code and run the old app to learn behavior: what a screen does, validation, edge cases, permissions, empty/error states, shortcuts, API calls and parameters. Write what you learned in prose in the area spec, then write new code from the spec.
- The import-ban lint and the similarity check in CI must pass. Never weaken, skip or work around them.

2) Full functional parity: when the project is done, everything apps/web does works in apps/web_new, with nothing missing or broken. This covers the OSS build, the cloud edition and the desktop build. The UI may be redesigned; no capability, rule or outcome may be lost.
- Parity is defined by the feature inventory (one row per capability, stable IDs) and proven by the parity suite, which runs the same scenario against both apps. A scenario passes on apps/web first, then must pass on apps/web_new.
- An issue is Done only when every inventory row it names is green on apps/web_new and all CI checks pass. No stubs, no skipped or weakened tests.
- If you find a behavior no inventory row covers, add a row. If a scenario would lock in an old bug, mark it "bug:" and link an issue.

Reference wiki (project pages): you do not need to read them up front. Look one up only when your task needs it. "Start here" (page d3df2fc2-740e-4397-85f0-7613f2433836) has the page map and where things live. Other pages: Reference, not source; Parity; Architecture; Stack and dependencies; Data layer; UI kit and editor; Platform and editions; Quality gates; Phases and migration; Decisions and open questions. List them with pidash page list --project NEWFRONT; read one with pidash page get <id> --project NEWFRONT. If a question is listed as open on "Decisions and open questions", do not decide it yourself.

Runs (binding):
- Branch from web-new-dev; PRs go into web-new-dev. Touch only the allowlisted paths (NEWFRONT-1) plus the extras your issue names.
- Open blockers are a hard stop: if pidash issue get shows has_open_blockers, note it in the workpad, run pidash issue wait, exit. A dependency you discover mid-run is recorded as an edge (pidash issue relate <this> --blocked-by <other>), not only in a comment.
- Review (In Review): assume the diff is wrong. Check it against the two goals, the issue's Done when, the area spec and the inventory rows it names; compare it with the old files the spec cites and reject anything translated rather than written. Two independent passes before deciding. Approved: move to In Test. Defects: list them and move to In Progress.
- Test (In Test): run every check the issue names. On pass, post "Ready to merge" and continue into the merge in the same run; there is no human gate. (a) Dependencies first: the PRs of this issue's blocked_by issues, and any PR this PR is based on, must be merged; if one is not, note it in the workpad, pidash issue wait on it, exit. (b) Rebase on the latest web-new-dev; resolve conflicts only in paths this issue owns; for shared code keep both sides, never drop or fork a helper; regenerate pnpm-lock.yaml with pnpm install instead of hand-merging it. (c) Re-verify: the named checks are green after the rebase and the diff stays inside the allowed paths. (d) gh pr merge <n> --admin --squash --delete-branch; if web-new-dev moved since the rebase, go back to (b), up to three times, then a process: comment. (e) Comment the merge commit SHA and move the issue to Done. If (b) or (c) fails, do not merge: comment the failure and move the issue to In Progress. An issue with no PR goes to Done once its checks pass. If a run finds an In Test issue whose latest comment is "Ready to merge" with no later failure, it is the merge run and starts at (a).
- Ending a run: never end a review or test run with the issue left where it is. Move it on (approved to In Test; pass to merge and Done; defects to In Progress). If you must wait for CI, a merge or another issue, stay and yield waiting_on_external, which keeps ticking.
- Environment: never set variables inline (VAR=value cmd); use export on its own line. Before any migrate, seed or destructive SQL, print the target database and stop if it is not your own scratch database.

Process problems (a rule you cannot follow, a tool that fails) go in a "process:" comment on NEWFRONT-1, never a silent workaround.
