## What this is

The rulebook for NEWFRONT: how issues are organized, who releases them, and which paths agents may touch. The two goals and the run rules (blockers, review, test and merge, ending a run) are in the project description, which every run already has. The design reference lives in the wiki pages ("Start here", page `d3df2fc2-740e-4397-85f0-7613f2433836`); read a page only when your task needs it.

This issue is never worked on as a task. Process problems go here as `process:` comments.

## Branch

All work goes into `web-new-dev` through PRs. A human merges `web-new-dev` into `main` at phase exits; agents never push to `main`.

## Paths agents may touch

Every issue may touch:

- `apps/web_new/**`
- `packages/kit/**`, `packages/api-client/**`
- `.ai_design/new_frontend_implementation/parity/**` (inventory, specs)
- `.github/workflows/web-new*.yml`
- `pnpm-lock.yaml`, only as regenerated by `pnpm install`

Some issues name extra paths in their body (for example `desktop/**` for F-07 and M-01, `apps/proxy/Caddyfile*` for F-09 and area gates, `data-testid` attributes in `apps/web` for oracle issues). Nothing else, ever. In particular: no other change to `apps/web`, the old `packages/*`, `apps/api`, `apps/live`, `apps/admin`, `apps/space`. A needed backend change is a new issue in PDASHOSS01 (OSS) or PRIVATEPI1 (cloud), related to your issue as a blocker.

CI fails a PR that touches paths outside this list plus the issue's named extras. Reviewers reject it too.

## Issue types

| Type | Label | What a run does |
|---|---|---|
| Rulebook | `kind:rulebook` | Never worked. |
| Decision / sign-off | `kind:decision` + `human` | A human decides and moves it to Done. Agents never work on these. |
| Foundation | `kind:foundation` | Single issue, never split. Builds shared infrastructure; later issues copy its patterns. |
| Inventory | `kind:inventory` | Lists every capability of one area as rows in `parity/inventory/<area>.md`. No code. |
| Oracle | `kind:oracle` | Writes parity scenarios for one area's rows and makes them green on `apps/web`. |
| Area epic | `kind:epic` | A container. Its one In Progress run is a **split run** that creates sub-issues (spec → contracts → slices → area gate) and moves the epic to In Review. The review run fixes the tree and moves it to **In Test, meaning "split accepted"**. Sub-issues run only while their epic is In Test. The area gate moves the epic to Done. |
| Sub-issue | epic's stage label | Does exactly what its body says; its row IDs are its Done when. |
| Migration | `kind:migration` | Switches the desktop app (M-01) or removes the old frontend (M-02). |

## Stages

Every issue carries a `stage:N` label. Stages are for reporting; **release is driven by blockers**: every dependency is a `blocked_by` edge.

| Stage | Contents |
|---|---|
| 0 | Decisions, foundation (F-01…F-11), inventories, oracle scenarios, inventory sign-offs |
| 1 | Epics: auth, shell, issues, comments, drafts |
| 2 | Epics: runners, agents (schedulers, prompts, assistant), notifications, desktop; M-01 desktop switch |
| 3 | Epics: views, archives, intake, cycles, modules, pages, estimates, analytics, stickies, exports, project settings, workspace settings, profile, cloud edition |
| 4 | Human acceptance pass; M-02 removal |

## Release and the coordinator

- **Backlog is inert.** Only the coordinator moves an issue from Backlog to In Progress, when: it is not labeled `human` or `kind:rulebook`; every `blocked_by` issue is Done; for a sub-issue, its epic is In Test. Nothing else releases work.
- Issues labeled `human` sit in Todo until a person moves them to Done.
- The coordinator is a project manager, not a developer: it releases, re-ticks stuck runs, re-dispatches failed ones, turns `process:` comments into issues, and posts a status report (per stage: Done / in flight / blocked, the parity report numbers, open human decisions). It never touches code.

## Environment safety

- Never set environment variables inline (`VAR=value cmd`); the agent shell drops secret-looking ones silently. Use `export VAR=value` on its own line or source an env file.
- Parity and contract suites run against your own local stack. Before any migrate, seed or destructive SQL, print the target database and stop if it is not your own scratch database.
