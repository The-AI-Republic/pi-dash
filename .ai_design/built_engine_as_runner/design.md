A runner with a bound run still cannot change pods, and no run's pod is ever rewritten (sections 7, 13). Every server change names its `rust-api/` counterpart (section 16).
- Revision 3.4 (review): defined which triggers count as human, stopped a refused run from arming the issue's clock, and made HA's re-point safe for legacy `managed_runner` runs.
- Revision 4.0 (product owner, 2026-11-05): **the design covers the engine only.** Issue work reaches an engine only through its pod: the owner turns pod work on per project (`Runner.pod_dispatch = pod_member`), and the PO-11 migration still does it for projects whose default is the built-in engine. The issue picker chooses a pod; no one can send an issue to "my engine" (sections 7, 11). The reason: revisions 3.3 and 3.4 built single-engine dispatch on HA's `Issue.assigned_runner`, but none of HA is implemented on the server (no Django or `rust-api/` code for it on `main` at `08be546d6`; only `apps/web_new` ships its UI), so this design depended on work nobody has built. Issues set to the built-in engine now migrate to pod-level `local_runner` (section 13). ## 2. Terms

- **CLI:** the `pidash` program. `pidash <command>` is the command line; `pidash __run` is the daemon.
- **Daemon:** the Pi Dash CLI daemon on a computer: one per OS user, installed in the standard location (`~/.local/bin` by the shell installer, `%LOCALAPPDATA%\Programs\pidash` by the PowerShell installer or MSI), configured under the standard XDG paths, and kept running by a user service (systemd, launchd, Windows). It holds the machine's credentials and hosts every runner on the computer.
- **App:** the Pi Dash desktop app (Tauri). A native client of the daemon over its local control socket.
- **Dev machine:** the `DevMachine` row backed by the daemon. One per computer and OS user.
- **Built-in engine:** the open-source OpenAI Codex, renamed `pidash-agent-engine`, shipped in the CLI release and driven by the daemon over `codex app-server`. Shown to users as "Built-in engine · <machine name>".
- **Engine runner:** a `Runner` row whose agent is the built-in engine (`provisioning = desktop_bundled` on the server, kept for compatibility; section 5). One per dev machine and project.
- **Own-agent runner:** a `Runner` row with `provisioning = manual` whose agent the user supplies (Claude Code, their own Codex, and so on).
- **Daemon credential:** the `MachineToken` the daemon holds per workspace. It authenticates the daemon, its runners and the CLI's commands to Pi Dash.
- **Engine credential:** a new per-machine credential, issued with the daemon credential, whose only use is to obtain short-lived model tokens for the engine (section 4.3).
- **Model token:** the short-lived OpenHub gateway token the engine presents on model calls. Held in the daemon's memory, never written to disk.
- **Legacy desktop machine:** a `DevMachine` with `provisioning = desktop_bundled`, created by builds before this design for the daemon the app ran as its child (one per computer and workspace). Merged away on upgrade (section 13).

## 3. Constraints the design works within

These are facts of the current model that the design keeps, because changing them is a larger project than this feature.

- A runner belongs to exactly one pod and a pod to exactly one project (`api/runner/models.py:52-176`, `:382-498`). The daemon enforces "one runner, one project" and an exclusive, non-nested working dir per runner (`runner/src/config/schema.rs:681-690`, `:733-754`).
- A runner executes one run at a time (`runner/src/daemon/supervisor.rs:1385-1402`).
- One dev machine is one daemon and one live session (`machine_session_one_active_per_machine`, `api/runner/models.py:752-757`). A `DevMachine` is user-scoped, not workspace-scoped, and holds at most one active `MachineToken` per workspace (`api/runner/models.py:334-335`, `:814`), so the server already models one machine serving several workspaces.
- Every runner is private. A runner only takes a run tied to its owner: created by the owner, already billed to the owner, on an issue the owner created or is assigned to, or from a scheduler binding the owner authored (`filter_runs_usable_by_runner`, `api/runner/services/permissions.py:83-123`). Lists and chat are owner-only.
- The daemon already drives several agents through one interface (`AgentKind`: Codex over `codex app-server`, Claude Code, Cursor Agent, OpenClaw, Grok; `runner/src/config/schema.rs:250`). The built-in engine is the Codex driver pointed at a bundled binary.
- **A run's pod never changes once the run exists.** The runner pod move is refused with `409 runner_busy` while any non-terminal run has `runner` or `pinned_runner` set to the runner (`api/runner/views/runners.py:397-417`; `:400-422` on `main`; tested in `tests/unit/runner/test_runner_pod_move.py`), because the matcher scans only the runner's current pod. The issue side refuses a pod change while the issue has an active run (`has_active_run`, `api/db/models/issue.py:236`; `api/app/serializers/issue.py:259`).
- **Assigning an issue to one runner is designed but not built.** `.ai_design/dedicated_runner_assignment/design.md` ("HA" below; PDASHOSS01-296, merged 2026-10-22) defines `Issue.assigned_runner`, `AgentRun.pin_kind`, `dispatch_wait`, `Project.dedicated_runner_lost_action` and decisions H-1 to H-9. None of it is implemented in Django or `rust-api/`: at `main` `08be546d6` none of those names appears under `apps/api/` or `rust-api/`. Only `apps/web_new` ships its UI (the pod and runner picker, the waiting banner, the AI Workers settings page). As written HA forbids `desktop_bundled` runners (E5, I3). **This design does not depend on HA:** engines get issue work through pods only (section 7). What an engine needs from HA, and HA from this design, is in HA's section "Engine runners (built-in engine)" (section 7.1).
- **The server is two codebases.** `rust-api/` on `main` is a Rust port of the Django backend that takes traffic one domain at a time, with the same semantics, while Python stays in place (`rust-api/README.md`). The runner domain is already ported: enrolment and desktop enrolment (`rust-api/crates/api/src/runner_enroll/`, `desktop.rs`), the usage rule (`crates/auth/src/permissions/runner.rs`), matching (`crates/api/src/orchestration.rs`), offline recovery and the pin-release sweep (`crates/jobs/src/runner_runs/offline_recovery.rs`), the runner list's `include_bundled` (`crates/api/src/runner_enroll/manage.rs:1159`) and `MANAGED_RUNNER_MAX_PER_USER_PROJECT` (`crates/db/src/config/registry.rs:327`, `settings.rs:1108`, `crates/services/src/dispatch/admission.rs:671`). Every server change in this design lands in both, or has a PIDASHCONV issue (section 16). Since 2026-11-04 `rust-api/` reads and writes through SeaORM (entities for every OSS table, #2896; the raw-SQL ratchet guard, #2881), and the runner endpoints moved to it in Batches 1a to 1g on 2026-11-04 (#2899 to #2916), so the Rust counterparts here are written with SeaORM in files those batches just changed.

These are facts of today that this design changes:

- The app runs its own daemon as a child process, one per workspace, under its app data with `PIDASH_CONFIG_DIR` and `PIDASH_DATA_DIR` overridden (`desktop/src-tauri/src/managed_runner.rs:97-104`, `:492-510`, `:668-672`), so it never meets a hand-installed daemon (`runner/src/util/paths.rs:36-46`). Today there is one desktop `DevMachine` per computer and workspace (`api/runner/views/desktop.py:108-125`), plus a separate `manual` one if the user also installed the CLI.
- The engine binary ships in the app bundle (`desktop/scripts/bundle_agents.py`, `prepare-agent.sh`), and its Codex config and model token are written by the app (`managed_runner.rs:368-405`). The model token comes from `POST /api/v1/users/me/ai-assistant/agent-token/`, which accepts desktop sessions only (`managed_runner/design.md` §14.3).
- A CLI install is bound to one workspace (`runner/src/config/schema.rs:41-48`), though each `[[runner]]` block already carries its own `workspace_slug` (`:116-120`).
- CLI credentials are plaintext files with mode 0600: the CLI token in `config.toml` `[cli].token`, the per-runner refresh tokens under `data/runners/<id>/` (`runner/src/config/file.rs:177-237`). Nothing uses the OS keychain. A `MachineToken` never expires; it can only be revoked (`api/runner/models.py:811-850`).
- Adding and removing a runner at runtime partly exists. Machine control's `CreateRunner` writes the block and starts the runner in-process with no restart (`runner/src/daemon/machine_control.rs:207-266`, `supervisor.rs:369-406`); the IPC request `RunnerActivateLocal` does the same for a block written locally (`ipc/server.rs:149`, `supervisor.rs:340-357`), and `RunnerRemoveLocal` removes one (`ipc/server.rs:278-302`, `supervisor.rs:1734-1800`). But `pidash runner add` and the TUI restart the whole service after writing (`cli/runner.rs:303-315`, `tui/views/modals/add_runner.rs:130`, `service/reload.rs:64-80`), and changing a runner's settings, its working dir included, has no in-process path (`tui/app.rs:782-789`; `ConfigPush` is a no-op, `cloud/protocol.rs:419-420`). The `instances` registry is not cleaned on removal (`supervisor.rs:335`, `:372`, `:403`), so a removed runner still shows in IPC status and re-adding the same id does nothing.
- A login with no stored machine id mints a new one (`ensure_dev_machine_id`, `runner/src/cli/runner_ops.rs:236-245`), and the server creates a new `DevMachine` for an unknown id (`api/runner/views/enrollment.py:72-95`). The `(owner, host_label)` lookup is reached only by legacy callers that send no id. So a daemon whose data was wiped becomes a new machine.
- Opening a machine session revokes the one already open (`api/runner/views/machine_sessions.py:88-98`, reason `evicted_by_new_session`). The daemon holds one machine token (`config.cli.token`) and hands it to every runner and to its machine client (`runner/src/daemon/supervisor.rs:92-104`, `:224`); the server binds a runner to the token's workspace (`api/runner/authentication.py:145`). So a daemon cannot serve two workspaces today.
- A pinned run is matched only within the pinned runner's _current_ pod (`api/runner/services/matcher.py:157-167`). Revoking a runner unpins its queued runs back to the pod (`api/runner/models.py:644-650`), and deleting it does the same through `on_delete=SET_NULL` (`:915-917`). Runs pinned to an offline `local_runner` are released to the pod after 300 s (`api/runner/tasks.py:125-145`).
- Dispatch admits a run to a runner when the run was created by or is owned by the runner's owner, or is on an issue the owner created or is assigned to, or comes from a scheduler binding the owner authored, whatever started it (`filter_runs_usable_by_runner`, `api/runner/services/permissions.py:103-121`). `AgentRun.trigger` records how a run was created (`api/runner/models.py:237-246`, `:972-977`).
- The open-source server already has a pluggable model seam that the cloud overlays: `agent_model_profile_for_user` and `agent_model_credential_for_user` (`api/ee/assistant/model_provider.py:71-110`). In the open-source build the profile is always unavailable. The kill switch `MANAGED_RUNNER_ENABLED` defaults to off (`api/core/agent_execution.py:46-54`).
- `pidash install` writes the caller's `PATH` into the service unit (`runner/src/service/mod.rs:29-45`). `pidash update` replaces only the `pidash` file and does not restart the daemon (`runner/src/cli/update.rs`). The CLI release has shell, PowerShell and MSI installers; there is no Homebrew formula (`dist-workspace.toml:11`).
- Every other `config.toml` change is applied by restarting the service and waiting for it to reconnect (`runner/src/service/reload.rs`), which stops every runner the daemon hosts.

## 4. The CLI, the engine and the app (point 1)

**Decisions:** one computer is one dev machine backed by one CLI daemon **[PO-1, decided]**; the built-in engine is part of the CLI **[PO-15, decided]**; the app is a native client of the daemon, and sign-in follows option A in section 4.6 **[PO-16, decided]**.

### 4.1 The three parts and how they relate

```
Pi Dash cloud ⇄ CLI daemon ──spawns / drives──► built-in engine ──model calls──► OpenHub gateway
                    ▲
                    │ local control socket (native, not through the cloud)
               desktop app            pidash commands, TUI
```

- **The CLI daemon** is the computer's runner host. It is installed, started and updated as itself, runs whether or not the app is open, holds the machine's credentials, and hosts every runner, engine and own-agent alike.
- **The built-in engine** is one of the agents the daemon can run. It ships in the CLI release, and the daemon starts it per run and drives it over `codex app-server`, exactly as it drives a user's own Codex. It has no identity on the server and never talks to the Pi Dash cloud; its only outside connection is model traffic to the OpenHub gateway, with a model token the daemon gives it.
- **The desktop app** is a native client of the daemon, like the TUI or `pidash status` but richer. It talks to the daemon over the local socket for local chat, runs, approvals, runner set-up and engine settings. It owns no daemon, no runner and no engine.
- **Independence.** The daemon and the engine work with no app installed (section 4.2). The app works as a cloud client with no daemon, and offers to set one up (section 4.7). The app never starts the daemon as its child, never stops it, and never deletes its config or credentials.
- **Install order does not matter.** CLI first or app first, the result is one daemon, one machine row, and engine and own-agent runners side by side.

### 4.2 The CLI on its own

A user with no desktop app gets the whole feature from the terminal:

1. Install the CLI with the existing shell or PowerShell installer or the MSI. The engine comes with it (section 4.5).
2. `pidash auth login`: the existing device-code sign-in in the browser. It now issues both the daemon credential and the engine credential (section 4.3). No second sign-in for the engine.
3. `pidash install` (installs the user service) and `pidash start`, as today.
4. `pidash runner add --agent engine --project <p>` turns the engine on for a project (section 5). `pidash runner add` with another agent adds an own-agent runner, as today.

Runs, pods and billing then behave as in sections 6 to 9, whether or not the user ever installs the app.

### 4.3 Credentials

**Two credentials from one sign-in.** **[PO-17, decided: two credentials, 60 and 14 days, `--engine`]**

|                | Daemon credential                                     | Engine credential                                                                                                      |
| -------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| What it is     | The existing `MachineToken`, one per workspace        | New, one per machine (the wallet is per user, not per workspace)                                                       |
| What it can do | Authenticate the daemon, its runners and CLI commands | Only exchange for a short-lived model token at the Pi Dash server                                                      |
| Lifetime       | 60 days                                               | 14 days                                                                                                                |
| Issued by      | `pidash auth login`                                   | `pidash auth login`, or `pidash login --engine` alone                                                                  |
| Revoked by     | `pidash auth logout`, "Remove this computer"          | `pidash auth logout --engine`, `pidash auth logout`, "Remove this computer", "Sign out the engine" on the machine page |

- **Why separate.** A leaked engine credential spends the wallet but cannot run tasks or read the workspace; a leaked daemon credential runs tasks but, alone, cannot spend. Each has its own expiry and can be revoked alone. The engine's shorter life bounds the wallet exposure.
- **`pidash login --engine`** (also `pidash auth login --engine`; `pidash login` is the existing alias) runs the same device-code flow but asks only for an engine credential. Use: renewing the engine without touching the daemon, or adding the engine to an install that signed in before this feature.

**How the engine credential is issued and bound.**

- **Model.** New `EngineCredential`: `user`, `dev_machine` (required), `token_hash` (SHA-256, the raw value is shown once), `fingerprint`, `created_at`, `expires_at`, `last_used_at`, `revoked_at`, `revoked_reason`. Raw values carry the prefix `ec_`. At most one live credential per `dev_machine` (partial unique constraint); issuing a new one revokes the previous one in the same transaction.
- **With `pidash auth login`.** The existing device flow (`api/authentication/views/cli/device.py`) issues the machine token and, in the same transaction, an engine credential for the same `dev_machine`, when the instance can serve the engine (below). The device-approval page says that it signs in both Pi Dash and the built-in engine on "<host>".
- **With `pidash login --engine`.** A device grant created with `scope = engine`. Redeeming it requires the request to also carry a live machine token, and the credential is bound to _that token's_ `dev_machine`, which must belong to the user who approved the grant. An approved code alone cannot mint a credential for any machine, and a stolen machine token alone cannot either, because a person must approve the grant.
- **Silent renewal by the app.** The app approves an engine grant with its own session, then hands the code to the daemon (`pidash login --engine --device-code-stdin`), which redeems it with its machine token as above. The server allows session approval of `scope = engine` grants only for a `dev_machine` owned by the session's user.
- **Workspace scope.** Device approval today picks the user's most recent workspace (`device.py:256-267`). Approval gains an explicit `workspace_slug`, which `pidash auth login --workspace` and the app pass; with none it keeps today's behaviour.
- **Engine sign-in states.** The server keeps one per machine, `DevMachine.engine_sign_in_state`, and the daemon mirrors it locally:

  | State                 | Meaning                                                                                                                                     | Silent renewal by the app                                                                                                                                                                                                                         |
  | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `never`               | The machine has never had an engine credential (an install from before this feature, or the instance could not serve the engine at sign-in) | No. The app shows a one-click "Turn on the built-in engine", which is an explicit sign-in.                                                                                                                                                        |
  | `active` / `expiring` | A live credential; `expiring` within three days                                                                                             | Yes, when `expiring`                                                                                                                                                                                                                              |
  | `expired`             | The credential reached its 14 days                                                                                                          | Yes                                                                                                                                                                                                                                               |
  | `signed_out`          | The user signed the engine out: `pidash auth logout --engine`, "Sign out the engine", or `pidash auth logout`                               | **No.** The server refuses session approval of `scope = engine` grants for the machine. Only an explicit engine sign-in clears it: `pidash login --engine` with browser approval, or the app's "Sign in the built-in engine" clicked by the user. |
  | `revoked`             | An admin or "Remove this computer" revoked it                                                                                               | No                                                                                                                                                                                                                                                |

- **Revocation.** `pidash auth logout --engine`, "Sign out the engine" on the machine page, removing the machine, and the user's sign-out of all sessions revoke it. Every issue, use and revocation is audited with the user and machine, never the raw value.
- **`pidash auth status`** shows both credentials and their expiry dates.
- **Absolute or sliding lifetimes.** **[PO-18, decided]** The daemon credential expires after 60 days _without use_, and each use renews it; the engine credential expires 14 days after it was issued, whatever its use. A fixed 60-day limit on the daemon credential would take every always-on CLI server offline every two months, a change from today, where it never expires. A fixed 14-day limit on the engine is the point of the shorter life. With the app signed in as the same user, the app renews the engine credential before it expires without asking (section 4.6), so only CLI-only users re-run `pidash login --engine`.
- **Expiry.** The daemon warns three days before the engine credential expires, in `pidash status`, the app and the machine page on the web. At expiry the machine's engine is paused automatically with the reason `engine_sign_in_required` (section 8), so pods route elsewhere. A run in flight continues until its current model token expires.

**Model profile and model tokens.**

- Both reuse the existing seam that the cloud already overlays (`api/ee/assistant/model_provider.py:71-110`): `agent_model_profile_for_user` for the profile and `agent_model_credential_for_user` for `(token, expires_at)`. No new provider setting is added.
- **Profile:** new `GET /api/v1/runner/engine/profile/`, authenticated by the daemon credential. It replaces the desktop-session-only profile endpoint (`api/assistant/views/agent_profile.py:41`) for new clients. The daemon fetches it at start, on engine credential issue and every 15 minutes, and writes the engine's Codex config from it.
- **Model token:** new `POST /api/v1/runner/engine/model-token/`, authenticated by the engine credential only. It returns `{token, expires_at}`, rate-limited and audited like today's desktop endpoint (`managed_runner/design.md` §14.3).
- **When the instance cannot serve the engine:** `MANAGED_RUNNER_ENABLED` is off, or the profile is unavailable (always the case in the open-source build, which has no OpenHub lane). Then the profile endpoint says so with its reason code, `pidash auth login` issues no engine credential, `EngineRunnerAdd` and `pidash runner add --agent engine` are refused with the reason, and existing engine runners are paused with it (section 8). BYOK for self-hosted instances is a later extension.
- The daemon fetches a model token when an engine run or chat starts and refreshes it before expiry. It keeps it **in memory only**. The engine's command-backed auth helper (today `pidash __managed model-token --file`, written into the engine config by `render_engine_config`, `managed_runner.rs:753-790`) becomes `pidash __engine model-token`, which asks the daemon over the socket. Nothing short-lived is written to disk, which removes today's `runtime/model.token` file.

**Storage in the OS keychain.** **[PO-19, decided: keychain where available]**

- The daemon and engine credentials are stored in the OS credential store: macOS Keychain, Windows Credential Manager, the Secret Service on Linux (GNOME Keyring, KWallet), through the `keyring` crate.
- A new setting `[auth] credentials_store = "auto" | "keyring" | "file"`, the same choice Codex offers (`cli_auth_credentials_store`). `auto`, the default, uses the keychain when it answers and falls back to a 0600 file otherwise, and `pidash doctor` reports which is in use. `keyring` refuses to fall back. `file` is today's behaviour.
- The fallback matters on headless Linux: a server with no desktop session usually has no Secret Service, and a systemd user service started without a login session may find the keyring locked. Claude Code falls back the same way on Linux (`~/.claude/.credentials.json`).
- Per-runner refresh tokens stay in their 0600 files in the first version. They rotate often, there can be 50 of them, and none can spend the wallet. They can move to the keychain later.
- This is not a complete defence. Any process running as the same OS user can usually ask the keychain for an item the daemon can read. What it adds is that the secret is no longer in a file that backups, sync tools, a copied home directory or a `cat` can pick up.

### 4.4 Discovery and compatibility

- The app connects to the daemon's control socket at the default path. A new IPC request, `Hello`, returns the daemon's version and IPC protocol version, the signed-in account (user id and cloud URL), the workspaces it holds credentials for, the engine's state (available, signed out, expiring, unavailable) and the machine id.
- The app ships a minimum daemon protocol version.
  - **Compatible:** the app cooperates.
  - **No answer to `Hello`** (a daemon from before this feature): treated as too old.
  - **Daemon too old:** the app offers "Update Pi Dash on this computer". It installs the CLI release it carries over the installed one, atomically, then restarts the service with the reload helper. When the install is in a location the app cannot write (an MSI install under `Program Files`, a system path), it tells the user how to update instead. It never updates silently.
  - **Daemon newer than the app understands:** the app asks the user to update the app.
  - Until resolved, the app's engine features are unavailable. The daemon, its engine runners and its own-agent runners keep working.

### 4.5 Shipping the engine with the CLI

- The CLI release (cargo-dist, `dist-workspace.toml`) carries `pidash-agent-engine` beside `pidash` for each platform, built from the same pinned Codex release the app bundles today. The desktop build scripts (`bundle_agents.py`, `prepare-agent.sh`) move to the CLI release pipeline.
- **Layout.** The engine is installed next to `pidash` but **never on `PATH`**, in a directory per engine version: `<install>/../lib/pidash/engine/<version>/` for the shell installer, `<install dir>\engine\<version>\` for the PowerShell installer and the MSI. The daemon finds it relative to its own executable; `[engine] binary` overrides that for development.
- **Updates.** `pidash update` installs the new engine version directory beside the old one, then replaces `pidash`, as today. A running daemon keeps using the engine path it resolved at start, so runs in flight are never given a swapped binary. The new engine is used from the next daemon start; the daemon deletes engine versions older than the one it runs once no run uses them.
- **[PO-20, decided]** The engine is in every release archive, so one install is enough and the two are signed and tested together.
- The app still carries a copy of the CLI release, so it can set the daemon up offline (section 4.7). On Windows, where the app's own copy cannot be put on `PATH` (`desktop/src-tauri/src/pidash_cli.rs:593-598`), it runs the network installer instead. The app no longer runs the engine itself.
- Codex is Apache-2.0; redistributing it in the CLI release needs its licence and notice files in the archive, as the app bundle already needs.

### 4.6 Signing in with the app (option A)

| Situation                                                | What happens                                                                                                                                                                                                                                                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **App first**                                            | The user signs in to the app in the browser, as today. When the app sets up the daemon (section 4.7) it signs the CLI in with a device grant it approves with its own session, passing the code on stdin (`pidash_cli_login`, existing). The grant issues both credentials. One sign-in in total. |
| **CLI first**                                            | The CLI is already signed in. The app asks for its own browser sign-in once, because the app's interface is the cloud web app and needs a web session. After that, `Hello` reports the same account and the app cooperates.                                                                       |
| **Engine credential expiring or expired, app signed in** | The app approves an engine-only device grant with its session and hands it to the daemon (`pidash login --engine --device-code-stdin`). No prompt. This silent renewal happens only in these two states (below).                                                                                  |
| **App sign-out**                                         | Signs out the app only. The daemon, the engine and all runners stay signed in, because they are independent. The sign-out dialog offers "Also sign out Pi Dash on this computer", which runs `pidash auth logout`.                                                                                |
| **CLI sign-out**                                         | The daemon and engine are signed out; the app stays signed in and shows the daemon as signed out, with "Sign in" (the app-first flow above).                                                                                                                                                      |

The reverse direction (a CLI sign-in signing the app in, with no browser) needs the server to turn a machine credential into a web session through a one-time grant handed over the socket. It is left for a follow-up with its own security review (section 16).

**Different accounts.** **[PO-13, decided]** When the daemon is signed in to a different Pi Dash account or cloud than the app, they do not cooperate in the first version. The app shows "Pi Dash on this computer is signed in as <account>", its engine features are unavailable, and everything served by the cloud works. It offers to sign the app in as that account, or "Sign Pi Dash on this computer in as me" when the daemon hosts no runners (otherwise it points to `pidash auth logout`). It never starts a second daemon.

### 4.7 App first: setting up the daemon

When the app finds no daemon, it offers "Set up Pi Dash on this computer" the first time the user turns the engine on for a project, adds a runner or opens local chat.

- The consent screen says that Pi Dash runs as a background service, that it keeps the user's runners, the built-in engine included, available when the app is closed, how to pause it, and how to remove it (`pidash uninstall`).
- Steps, all through the existing CLI rather than a second implementation:
  1. install the CLI release the app carries (`pidash` and the engine) into the official installer's location (`install_pidash_cli`, `cli_install_dir`, `desktop/src-tauri/src/pidash_cli.rs:227-232`), and put `pidash` on `PATH` as today;
  2. sign it in with a device grant the app approves (section 4.6);
  3. `pidash install` (the user service) and `pidash start`. The app runs `pidash install` with the user's login-shell `PATH` (from `$SHELL -lc 'printf %s "$PATH"'` on macOS and Linux), not its own GUI `PATH`, because the service unit records the caller's `PATH` (`runner/src/service/mod.rs:29-45`) and own-agent runners resolve their agents through it.
- The result is identical to a terminal install. This is the flow PIDESKAPP-114 found with no UI (`setUpCliForThisMachine`); it becomes the app's set-up path.
- On macOS the service is a launchd agent, so the OS shows a "background item added" notice. The consent screen says so.

### 4.8 When the user declines the service

**[PO-12, decided]** The service is required. If the user declines it, the app sets nothing up: there is no daemon, and so no built-in engine, local chat or own-agent runner on that computer. The app keeps working as a cloud client and offers set-up again from the same entry points. The app never runs the daemon as its own child, so there is no mode in which runners depend on the app being open.

### 4.9 Workspaces

One daemon serves every workspace the user enables on the computer. The server side already fits: the `DevMachine` is user-scoped and has one `MachineToken` per workspace, and every runner block carries its `workspace_slug`.

- The daemon holds one daemon credential per workspace and one engine credential for the machine, instead of the single workspace binding a CLI install has today (`runner/src/config/schema.rs:41-48`).
- `pidash auth login --workspace <slug>` adds a workspace rather than replacing the binding. The app adds one the same way, with a device grant scoped to that workspace.
- **One session per machine, any workspace's token.** The machine session stays one per machine (`machine_session_one_active_per_machine` is kept). The daemon opens it with the token of any workspace it holds; the control stream is already keyed by machine, not workspace (`api/runner/services/machine_outbox.py:84-97`). Machine-control commands name their workspace, and the daemon answers them with that workspace's token.
- **Runners use their own workspace's token.** Each runner authenticates with the token of its block's `workspace_slug`, so the server's binding of runner to token workspace (`api/runner/authentication.py:145`) and enrolment's workspace check (`enrollment.py:598-603`) stay as they are. The daemon replaces its single `shared_machine_token` (`supervisor.rs:92-104`) with a map from workspace to token; `MachineClient::machine_token()` (`runner/src/cloud/http.rs:1990`) and the identity check in `activate_configured` (`supervisor.rs:344-349`) take the workspace.
- **One workspace's token expires or is revoked:** only that workspace's runners stop, reported as `workspace_signed_out` in `pidash status` and the app. If that token was the one the session was opened with, the server revokes the session as today, and the daemon re-opens it at once with another workspace's token. The session ends only when no workspace token is left.
- `MAX_RUNNERS_PER_DAEMON` (50) is shared by engine and own-agent runners across all workspaces on the computer.

### 4.10 Identity

The daemon holds the machine's identity, exactly as a CLI install does today.

- The machine is created by the daemon's sign-in and found by its machine id and `host_label` = OS hostname, as today (`api/runner/views/enrollment.py:80-124`).
- `label` becomes user-editable, defaulting to the hostname. Add `PATCH` on the machine for `label` (no rename exists today).
- The app's `managed/device-id` and the `desktop-enroll` endpoint are no longer used by new builds; `desktop-enroll` stays for older builds only (section 13).
- **App data wiped:** nothing on the machine changes. The app only loses its own local chat history and settings.
- **Daemon data wiped:** the next sign-in mints a new machine id, so it creates a new machine, as today (section 3). Two computers can share a hostname, so the server never guesses that the new machine replaces an old one. Instead, recovery is explicit:
  - after sign-in, when the user has offline machines with the same `host_label` and no live session, `pidash auth login` and the app ask "Is this <label>, last seen <date>? Replace it"; on the web the old machine's page offers "Replaced by <new machine>";
  - confirming calls the merge endpoint from the old machine into the new one (section 13), which moves its runner rows, pins and pod membership, with the collision rule there;
  - the daemon then re-creates the local blocks of the moved engine runners from the server (an engine runner needs nothing local but its folder, allocated as in section 10). Own-agent runner rows cannot be rebuilt (their agent and folder were local); they show as offline with "Set up again on this computer" or remove;
  - declining leaves the old machine offline for the user to remove (PO-9).

### 4.11 How it appears in AI Dev Machines

One row per computer: name, status, last seen, and the engine's state (available, signed out, expiring on <date>, unavailable). Expanding it lists the built-in engine (with the projects it is on) and the own-agent runners. Actions are in section 11.

### 4.12 Rejected alternatives

- **The engine attached to the app** (revision 2). The app ships the engine and the daemon runs it only while the app is connected. It keeps "online only while the app is open", but the engine lives in one program and runs in another, needs a presence protocol and app-supplied paths, and does not exist for CLI-only users. Superseded by the product owner's choice.
- **Two daemons, the app's as its child** (today, and revision 1). Two machine rows for one computer, a hostname collision between them, and own-agent runners on the app's daemon go offline with the app.
- **Two daemons shown as one row.** Needs a hardware-derived key to recognise one computer from two installs, a relaxed one-session rule and UI merge logic.
- **Writing a new engine.** Not needed: the harness is the open-source Codex the app already ships.

## 5. Runner identity (point 2)

**Decision: the stored unit is one engine runner per machine and project.** A true single row per machine would require a runner to serve several pods and projects, which breaks the constraints in section 3 for every runner type.

- **A new agent kind.** `AgentKind::Engine` in the daemon's config: `agent.kind = "engine"`. The daemon resolves the bundled binary, the engine's `CODEX_HOME` (`<daemon data>/engine/<account>/codex-home`, never `~/.codex`) and the auth helper itself, so the block holds no app paths. It runs through the existing Codex driver. The engine's Codex config (gateway provider, policy, `managed_runner/design.md` §12.1) is written by the daemon; `render_engine_config` moves from `desktop/src-tauri/src/managed_runner.rs` to the runner. The model profile the engine uses (§12.2 there) is fetched by the daemon with its daemon credential.
- **Uniqueness replaces the cap.** At most one live engine runner per `(dev_machine, project)`. The enrolment reuse lookup (`api/runner/views/enrollment.py:705-720`) is keyed on machine and project instead of machine and pod, and `_managed_cap_error` with `MANAGED_RUNNER_MAX_PER_USER_PROJECT` is deleted. A second computer on the same account enrols its own row. This resolves PIDESKAPP-96.
- **No new machine limit.** Machines are created by the daemon's sign-in, the same path as any CLI install, so the existing limits on that path apply.
- **Enrol on use, not on page open.** Today every project route opened in the app enrols a runner (`desktop-overlay/apps/web/core/components/agent-runtime.tsx:65-141`). New rule: an engine runner is created when the user turns the engine on for a project: `pidash runner add --agent engine`, the first Run on this computer in the app, adding it to a pod, or the engine's project list in the app's settings.
- **How the app adds and removes them.** New IPC requests, `EngineRunnerAdd { workspace, project, working_dir }` and `EngineRunnerRemove { runner }`; the daemon enrols with the server using its daemon credential, writes the block under its config lock and validates it. The CLI does the same through `pidash runner add --agent engine` and `pidash runner remove`.
- **No restart to add or remove a runner.** A restart would stop every other run on the computer. Hot-add and removal already exist (section 3); the work is: `pidash runner add` and the TUI write the block and send `RunnerActivateLocal` instead of restarting; removal cleans the `instances` registry; a new per-runner reconfigure (stop that runner, rewrite its block, start it) serves `EngineRunnerSetWorkingDir` and any other per-runner setting. `EngineRunnerAdd` and `EngineRunnerRemove` are built on the same calls.
- **Removal exists.** "Remove from project" revokes the row: its held runs are cancelled and its queued pinned runs go back to their pod, as revoke does today (`Runner.revoke`, `api/runner/models.py:576-720`, the un-pin at `:678-685`, at `08be546d6`). The daemon reconciles at start and every 10 minutes: blocks whose server row is revoked are removed, and live engine runner rows of this machine with no local block are re-added, with a folder allocated as in section 10. The folder on disk is kept.
- **Local limit.** The daemon checks `MAX_RUNNERS_PER_DAEMON` (50) before calling the server, so the limit can no longer leave a half-enrolled runner. Together with the two points above this resolves PIDESKAPP-118.
- **Provisioning is per runner.** Today a runner inherits `provisioning` from its machine (`enrollment.py:701-704`). Now one machine hosts both kinds, so it follows the agent: an `engine` runner is created as an engine runner, any other as `manual`. On the new path the server creates an engine runner only for a machine with a live engine credential and an available profile (section 4.3). **Legacy exception:** older desktop builds enrol engine runners through `desktop-enroll` and `__managed enroll` on a legacy desktop machine, with no engine credential, and get model tokens from the desktop-session endpoint, exactly as today. The server keeps accepting that path for legacy desktop machines only, until `DESKTOP_MIN_VERSION_FOR_MANAGED_RUNNER` is raised past the first build with this feature (section 13). The stored value stays `desktop_bundled` for compatibility with older builds and history; it now means "built-in engine runner", and can be renamed later in a separate migration.
- **Naming.** The server assigns engine runner names: `builtin-<machine-slug>-<workspace-slug>-<project-identifier>`, lower-cased, truncated to the field length with a short hash of the project id when too long. The workspace is part of the name because project identifiers are unique only within a workspace (`project_unique_identifier_workspace_when_deleted_at_null`, `api/db/models/project.py:235-237`), while the daemon rejects duplicate names across its whole config (`ConfigError::DuplicateName`, `runner/src/config/schema.rs:713-717`) and one daemon now serves several workspaces. The server checks uniqueness across every live runner of the machine, not only per pod, and adds a numeric suffix on a clash (also keeping `runner_unique_name_per_pod`). Client-supplied names are ignored for engine runners. This removes the `desktop-desktop-<uuid>-<PROJECT>` names and the collision in PIDESKAPP-53. The UI shows "Built-in engine · <machine label>", so renaming the machine renames its engine everywhere. Engine runners are not renamed individually.

Two engine runners on one machine can run at the same time (two projects). That is today's behaviour and is kept. **[PO-7, decided]**

## 6. Executor model (point 3)

**Decision: Runner is the only executor.** **[PO-2, decided]** The built-in engine is a runner like any other that happens to have a fixed agent, and Cloud Agent is no longer offered for issue work, because it is not used to run issues today; it serves cloud chat. Which machine does the work is a dispatch question, answered by pods (section 7).

- **Selectable executors:** none. Issues and projects always run on runners (`local_runner`). The executor picker is removed from the issue and the project settings; what the user chooses is the pod. `managed_runner` and `cloud_agent` are no longer offered.
- **Cloud chat is untouched.** The `cloud_agent` code (`api/cloud_agent/`) keeps serving chat. Removing its issue-run path is separate cleanup, not part of this design.
- `Project.default_agent_executor`**:** `managed_runner` and `cloud_agent` rows become `local_runner`. The project's default pod then decides who runs the work (section 7). The `DEFAULT_AGENT_EXECUTOR` setting accepts only `local_runner`; the instance default is already `local_runner` (`api/core/agent_execution.py:26-31`).
- `Issue.agent_executor`**:** `managed_runner` and `cloud_agent` both become `local_runner`, pod-level: the issue keeps its `assigned_pod` and names no runner (section 13 states the consequence).
- `AgentRun.executor_kind`**:** new runs are `local_runner`. Whether a run used the engine is read from `run.runner.provisioning`. Existing rows keep `managed_runner` or `cloud_agent`; history is not rewritten and the enum values stay readable. The check constraint is unchanged. Runs already queued or running on `cloud_agent` finish there.
- **Policy that hung on the kind** moves to `Runner.provisioning`: availability reasons, the queued-run expiry, metering labels and prompt recipe aliases.
- **Compatibility:** the API keeps accepting `agent_executor = managed_runner` and `cloud_agent` from older clients and stores `local_runner`, pod-level, in both cases. An older desktop build that sets an issue to "Pi Dash Agent (desktop)" therefore gets a pod issue: it runs on whichever eligible runner of its pod takes it, the caller's own engine only when that engine is a pod member (section 7). Before this design it ran on the caller's own desktop; no runner is named, because naming one needs HA (section 7.1). The server cannot tell old desktop builds from new clients on the shared project serializer (`api/app/serializers/project.py:47-54`), so `agent_executor_options` keeps returning the old entries to everyone, each marked `deprecated: true`; new web and desktop builds hide deprecated entries, and old builds, which ignore the flag, keep showing them. The entries and the translation are removed once `DESKTOP_MIN_VERSION_FOR_MANAGED_RUNNER` is raised past the first build with this feature.

## 7. Dispatch and pods (point 4)

**Decision: an engine gets issue work only as a member of its pod.** **[revision 4.0, product owner]** The issue's execution picker chooses a pod (section 11), and the pod's matcher chooses the runner. There is no way to send an issue, or one run of it, to a specific engine. That needs HA's `Issue.assigned_runner`, which is not built (section 3); section 7.1 says where it went.

This differs from today, where the engine is resolved from whoever the run is created for (`api/orchestration/scheduling.py:938-948`): an issue set to the built-in engine runs on each person's own desktop. After this design that issue is an ordinary pod issue (section 13).

**Pods.**

- An engine runner is structurally always in a pod: the project's default pod at enrolment. A new `Runner.pod_dispatch` field says whether it takes pod work: `pinned_only` (default for engine runners) or `pod_member` (default for own-agent runners, which is their behaviour today).
- A `pinned_only` engine takes no new issue work. It serves only the legacy `managed_runner` runs already pinned to it (section 13) and chat (section 12). The value keeps its name because HA's engine section uses it for an engine that takes only the issues dedicated to it. The UI calls it "Pod work: off".
- "Add to pod" sets the pod and `pod_member`. "Remove from pod" sets `pinned_only`. Moving between pods uses the existing owner-only `PATCH` (`api/runner/views/runners.py:366-429` at `08be546d6`), restricted to pods of the same project for engine runners.
- **The pod-move guard stays.** The `PATCH` keeps refusing a move with `409 runner_busy` while any non-terminal run has `runner` or `pinned_runner` set to the runner (section 3). No run's `pod` is ever rewritten. To move a runner that has waiting runs, the owner first releases or cancels them, or waits for them to finish; the refusal lists them. Revision 3.2's rewrite of queued runs' `pod` is dropped.
- Only the owner can do any of this. Workspace admins cannot add someone's engine to a pod.
- Adding another computer's engine to a project it is not yet on requires turning it on from that computer. Doing it remotely while that computer is online can reuse the machine-control create path later; it is not in the first version.

**Locality pins to engines.** Locality pins (today's `_pinned_runner_for` in `api/orchestration/service.py`, which keeps a follow-up where the repo is on disk) are unchanged for own-agent runners. For an engine they follow its pod membership:

- a continuation is pinned to an engine for locality only when the engine is a `pod_member` and not paused; otherwise it is created unpinned in the pod;
- an engine takes a locality pin to itself under the same conditions and the usage rule in section 8;
- when the owner turns the engine's pod work off or pauses it, or it is paused automatically, the same transaction releases its queued locality pins to the pod, so none waits for the offline-pin sweep. The pod of those runs is unchanged.

**Matching** (`api/runner/services/matcher.py`):

- An engine runner that is a `pod_member` takes runs pinned to it for locality and unpinned runs in its pod. All of them must pass the usage rule in section 8. A `pinned_only` engine takes only legacy `managed_runner` runs pinned to it.
- The exclusion of engine runners from pod drains (`matcher.py:105` at `08be546d6`, `:109` at the baseline) and the kind split in `next_for_runner` (`:169-172`, `:173-176` at the baseline) are replaced by the rule above. Legacy queued `managed_runner` runs are still served to the runner they are pinned to (section 13).
- **Ranking:** **[PO-4, decided]** an engine that is a pod member ranks equally with ordinary runners: when several eligible runners are idle, the matcher's existing order picks one, whatever its agent. The consequence is stated plainly: an idle engine can take pod work while the owner's own agent is idle too, and that work spends the wallet. An owner who wants the engine off pod work keeps it `pinned_only`; until HA's engine section is built, such an engine runs no issues at all.

### 7.1 Dedicating an issue to one engine: moved to the dedicated-runner design

Revisions 3.3 and 3.4 let a person dedicate an issue to one engine through HA's `Issue.assigned_runner`. Revision 4.0 takes that out of this design, because HA has no server implementation, and moves it to HA's new section "Engine runners (built-in engine)" (`.ai_design/dedicated_runner_assignment/design.md` §23). That section is built with HA, **after** this design is implemented and merged (section 16), on top of `pod_dispatch`, the engine usage rule and the machine pause fields as they are on `main` by then.

What moved to HA §23:

- lifting E5 and I3 for `desktop_bundled` engine runners, and dropping the `runner_desktop_bundled` code;
- the engine usage rule (section 8) in place of "not `desktop_bundled`" in HA's dedicated preflight (§9.4) and its `fall_back` order (§13.1);
- PO-10: a human-triggered run the engine rule excludes is refused at creation with `assigned_runner_not_owner`, with "Run on my engine instead" and "Run on any runner in <pod> once";
- the rule that a refused human event leaves the issue's clock as it was, so no tick later starts the refused run;
- `dispatch_wait.reason = runner_paused` with `pause_reason`;
- refusing to move a runner to another project's pod while issues are dedicated to it (every runner);
- the picker's runner level listing engines as "Built-in engine · <machine>", with no executor peers;
- PO-22 to PO-25: adopting H-1 (wait for an offline engine, no timeout), H-2 (the lost-runner rule), H-8 (who may release) and the other HA rules for engines, restated in HA as decisions for the product owner to confirm;
- the scenarios that need a dedicated engine (revision 3.4's 8, 10, 18, 20, 24, 26 and 27, and the dedicated parts of 9 and 14).

Dropped rather than moved: the backfill of `assigned_runner` for issues set to the built-in engine (they migrate pod-level, section 13), and the legacy `managed_runner` exemption from HA's I4 and re-point, which HA §23 shows is no longer needed.

## 8. Who may use it, and who pays (point 5)

- **Who pays:** always the engine's owner, through their OpenHub wallet. The model token is obtained with the owner's engine credential, and `AgentRun.owner` is already set from the runner's owner at assignment.
- **Who can cause a run:** the owner. An engine runner takes a run only when one of these holds: **[PO-3, decided]**
  - the owner created the run (clicked Run, from any client);
  - the run is automatic (tick or scheduler) and is on an issue the owner created or is assigned to, or comes from a scheduler binding the owner authored.

- A teammate clicking Run on the owner's issue does not start a run on the owner's engine. This is stricter than the rule for ordinary runners, which would allow it.
- **Where the rule is enforced.** Today's usage rule admits any run on the owner's issues, whoever started it (section 3), so it must change in two places, both reading the trigger (human versus automatic) and the runner's `provisioning`:
  - **dispatch:** `filter_runs_usable_by_runner` gains an engine branch. For an engine runner it admits runs created by the owner, automatic runs on issues the owner created or is assigned to, and runs from scheduler bindings the owner authored; a human-triggered run created by someone else is admitted only when the owner's opt-in below is on;
  - **preflight:** `pod_has_runner_for_issue_principal` (`api/runner/services/matcher.py:358` at `08be546d6`) and `preflight_eligibility_or_bounce` (`api/orchestration/scheduling.py:959`) count an engine as eligible for a principal only when it is a `pod_member` and the same rule admits the run, so an issue is not left queued for an engine that will never take it. The run does not exist yet at preflight; `preflight_eligibility_or_bounce` already receives the trigger as `triggered_by`, and passes it on.

  **Human versus automatic** is the existing split in `api/runner/models.py:239-280` (at `08be546d6`; `HUMAN_TRIGGERS` at `:261-268`): `state_transition`, `run_ai`, `comment_and_run` and `direct` are human; `tick` and `scheduler` are automatic. `created_by` cannot be used for this, because a human-looking creator is resolved for automatic runs too. A state move made by a run from inside itself (`moved_by_run`, `api/orchestration/service.py:181-243`) creates no entry run; it queues the entry on the clock, which creates it as a tick. So an engine's own implement, review and test hand-offs are automatic and admitted, while a person dragging the issue to In Progress is a human `state_transition`.

  **A teammate's human event in a pod.** When no runner of the pod would take the teammate's run (for example the owner's engine is the only member and the opt-in is off), the existing preflight bounces the issue to Backlog with its system comment (`service.py:286`), which also stops the clock. When another runner would take it, the run is created and that runner takes it. Revision 3.4's separate clock rule was needed only for issues dedicated to an engine and moved with them (section 7.1).

  A queued pod run that an engine stops admitting while it waits (the owner is removed from the assignees, or turns the opt-in off) stays in the pod's shared queue for another runner, as it would for an ordinary runner today.

- **Where the opt-in lives:** `DevMachine.engine_team_runs` (boolean, default off), set by the owner on the machine page or in the app. It applies to all of that machine's engine runners.
- **Unattended use is now normal.** The engine runs whenever the daemon runs, not only while the app is open, so these controls carry the whole weight of protecting the wallet.
- **Owner controls:**
  - pod work is off until the owner turns it on, per project (the one exception is the migration of projects whose default is the built-in engine today, section 13);
  - a per-machine "Pause the built-in engine" switch, from the app, the web machine page or a new `pidash engine pause`. It is stored **on the machine**, not copied to runner rows: `DevMachine.engine_paused_by_owner`. Engine runners created or re-added later are therefore paused too, with no copy to forget;
  - an automatic pause, also on the machine: `DevMachine.engine_auto_pause_reason` (`engine_sign_in_required`, `gateway_session_revoked`, `wallet_empty`, `profile_unavailable`, `engine_disabled`, or empty). The daemon reports its engine state in the machine session heartbeat; the server sets the reason from that report and from the model-token endpoint's own failures (an empty wallet, an expired credential), and clears it when they recover. The owner's switch and the automatic reason are separate fields, so clearing one never undoes the other;
  - the matcher treats an engine runner as paused when either is set, by reading its machine; `Runner.dispatch_paused` stays for per-runner pauses of any runner;
  - an opt-in "Teammates can start runs on my issues", which applies the ordinary-runner rule;
  - removing the engine from a project, signing out the engine, or removing the machine.

- **Spending limit.** **[PO-21, decided]** None in this design beyond the wallet balance and the controls above. Limits on unattended spending need a systematic solution across the product, which is designed separately.
- **Issue work reaches an engine only through its pod.** Project defaults, ticks, Run AI, Comment & Run and schedulers cannot reach an engine whose owner has not made it a pod member, and then only for the owner's own work as defined above.
- **BYOK:** unchanged. The engine supports the OpenHub lane only (`managed_runner/design.md` §12.2), because no stored key is returned to a client. A BYOK user's engine does not come online and is shown with the existing reason.
- Sharing an engine with a team is not part of this design. No runner can be shared today.

## 9. Availability (point 6)

- **Legacy desktop machines** (older app builds, section 5) keep today's availability and token delivery until they are merged or retired: no engine credential is required; the app fetches model tokens from the desktop-session endpoint and the profile from the desktop-session profile endpoint, as today. Of the automatic pause reasons, `wallet_empty`, `profile_unavailable` and `engine_disabled` apply, set by the server from those endpoints' failures; `engine_sign_in_required` does not. The owner's pause applies as for any machine.
- **When an engine runner is online** (on a new-path machine): `MANAGED_RUNNER_ENABLED` is on, the daemon is online, the engine credential is valid, the model profile is available, and neither the runner nor its machine's engine is paused (section 8). The app is not involved: closing it changes nothing. This drops `managed_runner/design.md` §5's rule that the engine is "online exactly while the desktop app is open" **[PO-15, decided]**.
- **Pod work:** an offline engine is an offline runner. Unpinned runs go to whichever eligible runner is online; they never wait for the engine in particular.
- **Structural check:** `pod_has_runner_for_issue_principal` counts an engine runner as a registered runner for its owner only when it is a `pod_member`. A pod whose only eligible runner is an offline engine therefore queues the run rather than bouncing the issue to Backlog, as for ordinary runners; a pod whose only engine is `pinned_only` does not count it, and bounces.
- **Paused engine** (by the owner, or automatically for an expired engine credential, a revoked gateway session, an empty wallet or a missing model profile): treated as offline for matching, and its queued locality pins are released to the pod (section 7). Pod runs go to another eligible runner or wait in the pod. The machine page, the app and `pidash status` show the reason.
- **Legacy queued runs.** Runs created before the upgrade with `executor_kind = managed_runner` keep today's handling until they end: `error_code = desktop_not_connected` while the desktop is closed, and the sweep in `managed_runner/tasks.py` fails them after `MANAGED_RUNNER_QUEUED_MAX_AGE_SECS` (12 h). No new run is created with that kind (section 6), so this queue empties out and the sweep can be removed in a later release. Its reason text (`_MANAGED_UNAVAILABLE_DETAIL`, `api/app/serializers/issue.py:90-100`) says "Open the Pi Dash desktop app to run on this computer", which stays true for a legacy desktop machine; the web issue panel does not show it today (`issue-detail/agent-status.tsx:196-201`).
- **Daemon stopped mid-run** (service stop, update, computer shut down): the same as for any runner today. The daemon's graceful stop lets the current run finish for `MANAGED_RUNNER_GRACEFUL_STOP_SECS`, and the existing reaper handles anything left.

## 10. Default work dir (point 7)

**Boundary with PIDESKAPP-42.** PIDESKAPP-42 owns the default root location and the folder layout below a root; with the engine in the CLI it decides them under the daemon's data directory instead of the app's. This design owns the setting, its validation, how it reaches the runner and what a change does. A custom root uses the same layout below it as the default root.

- **Where it lives:** in the daemon's config, `[engine] task_root`. It is not stored on the server and not per project, because it is a path on one computer.
- **Default:** unset, meaning the default task root from PIDESKAPP-42. Until that lands, `<daemon data>/engine/workdirs`.
- **Where it is edited:** a new `pidash config set engine-task-root <path>`, or a "Built-in engine" section in the app's settings with a folder picker, which sends it to the daemon over the socket. The app has no settings page and no folder-picker permission today; both are part of this work.
- **Per-project allocation.** The root is a parent, never a runner's working dir itself. Turning the engine on for a project allocates `<root>/<workspace-slug>/<project-identifier>/`; if that path is already some runner's working dir or exists and is not empty, a numeric suffix is added. The allocated folder must pass the existing per-runner rule: exclusive and not nested in or around another runner's working dir (`runner/src/config/schema.rs:733-754`).
- **Validation of the root,** done by the daemon, never by the app's webview:
  - absolute, canonicalised, an existing or creatable directory, writable (probe file);
  - not a filesystem root or the home directory itself;
  - not inside the daemon's config directory, the engine home or the app's own data. Inside the daemon's data directory only the default, `<daemon data>/engine/workdirs`, is allowed;
  - not inside another runner's working dir. It may contain other runners' working dirs, engine or own-agent, because the allocated per-project folders are checked one by one above;
  - short enough for the deepest project path on Windows.
  - A network or removable drive is allowed with a warning. A failed check leaves the old value in place and reports which rule failed.

- **Effect of a change:** **[PO-6, decided]**
  - nothing is moved or deleted;
  - projects the engine is turned on for afterwards use the new root;
  - projects already set up keep their current folder. The app's settings and `pidash runner list` show each project with its folder. "Use the default location" rebinds a project to the new root with a fresh folder and leaves the old one on disk; "Switch all" does it for every project.

- **How it reaches the runner:**
  - new projects: the folder allocated as above, or the working dir given to `EngineRunnerAdd` or `pidash runner add --agent engine --working-dir`, which must pass the per-runner rule;
  - existing projects: a new IPC request `EngineRunnerSetWorkingDir { runner, working_dir }` (CLI: `pidash runner set-working-dir`) that rewrites the block under the config lock, re-runs schema validation and restarts only that runner (the per-runner reconfigure in section 5), and only while it is idle. A daemon restart is not acceptable here, because it would also stop other runs;
  - the runner reports the canonical path at session attach and the server stores it in `dev_metadata.working_dir` (`api/runner/services/session_service.py:62-93`), so the runner's re-attach keeps the server's copy accurate. The server only displays it.

- **Per-project folder chosen by the user** (pointing the engine at an existing local clone) uses the same command and is left as a follow-up.
- The chat working directory is not covered by this setting. It belongs to PIDESKAPP-42.

## 12. Chat routing (point 9) and the user's own agent (point 10)

### 12.1 Chat routing

The transport is chosen per runner, not once for the app.

| Chat target                                                   | Transport                   | Sessions stored         | Working folder                                                          |
| ------------------------------------------------------------- | --------------------------- | ----------------------- | ----------------------------------------------------------------------- |
| This computer's built-in engine (the "This computer" contact) | Local socket, app to daemon | Local, on this computer | Chat folder (PIDESKAPP-42)                                              |
| An own-agent runner on this computer                          | Server (HTTP + SSE)         | Server                  | That runner's work dir                                                  |
| Any runner on another computer, including its built-in engine | Server                      | Server                  | That runner's work dir, i.e. the project's task folder on that computer |

- **Native local chat.** The app talks to this computer's engine the way the ChatGPT app talks to Codex: straight to the daemon over the local socket, with the cloud involved only for model calls. The IPC requests already exist (`ChatWarm`, `ChatSend`, `ChatCancel`, `ChatClose`, `ChatDecide`, `runner/src/ipc/server.rs:313-390`) and the app already uses them (`LocalChatTransport`).
- **Implementation shape:** `registerLocalChatTransport` installs a routing transport that sends the built-in contact's sessions to `LocalChatTransport` and everything else to the cloud transport, in place of the global swap at `desktop-overlay/apps/web/core/services/local-chat-transport.ts:714-722`. Session-scoped calls resolve the owner transport from the session. Approvals follow the same split.
- **No duplicates:** this computer's own engine runner rows are not listed under "Runners" on this computer; they are represented by the local contact. On the web and on other computers they are listed per project as "Built-in engine · <machine> · <project>".
- **Chatting with another computer's engine** needs no new server work: server-routed chat already accepts an engine runner for its owner (`api/runner/views/chat.py:174-186` has no provisioning check); only the list hid it. It is billed to the same owner. The composer is disabled while that computer is offline, as for any runner.
- **Local chat no longer borrows a project's runner.** Today a local chat turn runs on whichever project runner the daemon resolves, which fails once the daemon hosts two (PIDESKAPP-41), forces chat to enrol a project (PIDESKAPP-14), and blocks chat for the length of a run (PIDESKAPP-101). The daemon gets a machine-level engine profile (engine binary, engine home, model token from its engine credential) of its own. IPC chat with an absolute folder runs on that profile, with no project runner and no shared busy flag. The app guarantees the chat folder is outside every task folder (PIDESKAPP-25). **[PO-8, decided]**
- Server-routed chat to a runner that is busy with a run still answers `runner_busy`, because that chat shares the run's folder. The UI should say so. The server comment claiming the two run concurrently (`api/runner/views/chat.py:247-251`) is wrong and should be corrected.

### 12.2 The user's own agent on the computer

Own-agent runners are ordinary runners on the same daemon. Nothing about them depends on the app.

- **Set-up from the app:** the existing Add-runner modal already creates a runner remotely on a machine that is online for control (`add-runner-modal.tsx`, `MachineMsg::CreateRunner`, `runner/src/daemon/machine_control.rs:156-230`). In the app, "Add runner" preselects this computer and offers a folder picker for the work dir. The user picks project, pod, agent and folder. If no daemon exists yet, the set-up in section 4.7 runs first.
- **Set-up from the terminal:** `pidash runner add`, as today. Both paths write the same daemon's config, so the app, the TUI and the web all see the same runners.
- **What this requires:**
  - the daemon must find the user's agent binary. A service records the `PATH` of whoever ran `pidash install` (`runner/src/service/mod.rs:29-45`); a GUI app's `PATH` lacks the user's shell setup (notably on macOS). Two fixes, both needed: the app installs the service with the user's login-shell `PATH` (section 4.7), and every runner add, from the app, the terminal or the cloud, resolves the agent binary to an absolute path and stores it in the block, with a doctor check;
  - adding a runner must not restart the daemon (section 5).

- **Coexistence with the engine:** same daemon, separate runners, separate work dirs (enforced by config validation across every runner on the computer), separate agent credentials. Own-agent runners keep today's dispatch behaviour.
- **PIDESKAPP-114:** its `setUpCliForThisMachine` flow becomes the daemon set-up in section 4.7. It no longer creates a second machine. PIDESKAPP-114 is rescoped to giving that flow its UI.

2. For each legacy tree `<app-data>/managed/pidash/<workspace>/`: make sure the daemon has a credential for that workspace (section 4.9), then call the merge endpoint from the legacy machine into the daemon's machine.
3. For each engine runner block in that tree, send `EngineRunnerAdd` with the block's project and working dir. The server's reuse lookup returns the merged row, so the runner keeps its id, pods, pins and folder.
4. Move the engine's home for the signed-in account (`managed/accounts/<account-key>/codex-home`, the engine's own transcripts) into the daemon's engine home for that account, so earlier local chats can be resumed. Homes of other accounts stay where they are.
5. Delete the legacy tree's `config.toml` and credentials and `runtime/model.token`. Task folders stay where they are.

Also: names are refreshed from the server (section 5); enrol-on-open stops; `managed/device-id` is no longer read and can be deleted after a successful merge; the app's local chat history is untouched. Whether task folders move under the PIDESKAPP-42 layout is that design's decision; this design only requires that a runner's bound folder keeps resolving.

## 18. Acceptance scenarios

The feature is done when these pass end to end. Each names the sections it checks.

1. **CLI only.** A user with no app installs the CLI, runs `pidash auth login`, `pidash install`, `pidash runner add --agent engine --project P`, and turns pod work on for P; an issue of theirs in P's pod runs on the engine and is billed to them. (4.2, 4.3, 5, 7)
2. **App only.** A user with no CLI signs in to the app, accepts set-up, and runs the same issue from the app. One browser sign-in in total; `pidash auth status` in a terminal shows both credentials. (4.6, 4.7)
3. **CLI first, then app.** The CLI is signed in; the app needs one browser sign-in, then shows the existing runners and uses the same daemon. No second machine row. (4.4, 4.6)
4. **Different accounts.** The CLI is signed in as A, the app as B. The app refuses to cooperate, says why, and starts no second daemon. (4.6)
5. **Two workspaces.** One daemon has engine runners in workspaces W1 and W2, both with a project called APP. Both run; their names differ; revoking W1's token stops only W1's runners and the session stays up. (4.9, 5)
6. **Two computers.** The same account turns the engine on for project P on two computers, both with pod work on; the owner's pod issues go to whichever is idle; each machine's engine is named by machine. (5, 7; PIDESKAPP-96)
7. **Teammate click.** A teammate clicks Run on the owner's issue in a pod where the owner's engine is a member and idle: the run does not go to the engine unless the owner's opt-in is on. (8)
8. **Engine removed.** A pod-member engine has a continuation pinned to it for locality; the owner removes the engine from the project. The run goes back to the pod's shared queue and another eligible runner takes it. (5, 7)
9. **Pod move.** An engine runner with no bound run moves to another pod of the same project; its next run comes from the new pod. While a run is queued pinned to it, the move is refused with `runner_busy` and the refusal lists the run; after the run is released or cancelled, the move succeeds. A move to another project's pod is refused for an engine runner. (7)
10. **Offline engine in a pod.** The owner's engine is offline and the owner's own-agent runner in the same pod is online: the owner's run goes to the own-agent runner. With the engine the only eligible member, the run waits in the pod's shared queue, the issue is not bounced, and the run starts on the engine when the daemon reconnects. (7, 9)
11. **Engine credential expiry.** With the app closed, the engine credential expires: engine runners pause with `engine_sign_in_required`, own-agent runners keep working, and `pidash login --engine` restores the engine without touching the daemon credential. With the app open and signed in, it is renewed before expiry with no prompt. (4.3, 8)
12. **Machine pause.** The owner pauses the engine, then turns it on for a new project; the new engine runner is paused too. (8)
13. **Keychain fallback.** On a headless Linux server, `credentials_store = auto` stores credentials in 0600 files and `pidash doctor` says so; on a desktop session they go to the Secret Service. (4.3)
14. **Upgrade with CLI before app.** A computer has a legacy desktop machine with an engine on P in pod A, and the user also turned the engine on for P from the new CLI, in pod B. A continuation is pinned to the legacy engine for locality in pod A. After the app upgrades, one machine remains with one engine runner for P; the continuation was released to pod A, and no run's `pod` was rewritten. Running the migration again changes nothing. (13)
15. **Daemon data wiped.** After `pidash auth login` on the same computer, the user is asked whether it replaces the old machine; confirming restores the engine runners with their pins and pod membership. (4.10, 13)
16. **Old desktop build.** An app build from before this feature, against the new server, still enrols and runs on its engine through the legacy path. When it sets an issue to "Pi Dash Agent (desktop)", the server stores `local_runner`, pod-level, and the issue's next run is dispatched in its pod. (5, 6, 13)
17. **Work dir.** With the default task root, turning the engine on for two projects allocates two folders under `<daemon data>/engine/workdirs`; changing the root leaves both in place; a new project uses the new root. (10)
18. **Issue set to the built-in engine.** After the server upgrade, an issue that was set to the built-in engine is `local_runner` with its pod and no runner. Its creator's next Run goes to an eligible pod member, the creator's engine when it is a pod member; when no member could serve it, the issue is bounced to Backlog with the system comment. (6, 13)
19. **Engine continuation.** A pod-member engine takes an unpinned run; its continuation is pinned to it and it takes it. The owner then turns pod work off: the queued continuation goes back to the pod at once. (7)
20. **Automatic run on a pod-member engine.** A tick on the owner's issue in a pod where the owner's engine is the only member: the run goes to the engine and preflight does not bounce. With the engine `pinned_only`, preflight bounces the issue to Backlog with its comment. (7, 8, 9)
21. **Explicit engine sign-out with the app open.** The user runs `pidash auth logout --engine` while the app is open and signed in: the app does not renew the credential, shows the engine as signed out, and offers "Sign in the built-in engine". (4.3, 4.6)
22. **Legacy build availability.** An old app build's engine runner is offline when the app is closed and online when it is open, takes runs with model tokens from the desktop-session endpoint, and pauses when the wallet is empty. (5, 9)
23. **Update mid-run.** `pidash update` during an engine run leaves the run on its engine binary; the next run after a daemon restart uses the new engine. (4.5)
24. **Teammate state move.** A teammate drags the owner's issue from Todo to In Progress in a pod whose only member is the owner's engine, opt-in off: preflight bounces the issue to Backlog with its comment, and no tick starts a run on the engine afterwards.
